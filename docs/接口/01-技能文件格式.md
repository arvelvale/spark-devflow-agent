# 接口 1：技能文件格式（`skills/<name>/SKILL.md`）

状态：**已冻结 v1（2026-09-24 晨熠确认）**。只增不改，要改先找负责人。代码侧校验在 `agent/skills.py`，改格式要同时改那里和 `tests/test_skills.py`。

参照 NVIDIA 官方 `rag-blueprint` 技能（`reference/nvidia-skills/rag-blueprint/SKILL.md`）：frontmatter 放机读元数据，正文是"薄路由"，细节放 `references/` 按需加载。

## 目录结构

```
skills/
  issue-breakdown/
    SKILL.md            # 必需：frontmatter + 正文
    references/         # 可选：正文里按需引用的细节文档，不会自动进上下文
      output-format.md
```

## frontmatter 字段

```yaml
---
name: issue-breakdown                 # 必填。kebab-case，必须等于目录名
description: >-                       # 必填。≤ 300 字。触发词放最前面（JEV 技能选择直接把它当选项描述）
  拆解 / 拆任务 / breakdown：把一个 Linear issue 或需求文档拆成结构化子任务提案（含验收标准），确认后写回 Linear。
version: 0.1.0                        # 必填。改正文或触发范围时 +0.1.0
argument-hint: "<issue 编号，如 DAY-12；或一段需求文字>"   # 选填。给用户和面板看的参数提示
model: auto                           # 选填，默认 auto。auto=交给路由决定；local=强制本地；cloud=强制 step-5
allowed-tools:                        # 必填（可为空列表）。见下方"工具白名单语义"
  - linear_get_issue
  - linear_create_issue
triggers:                             # 必填，≥ 2 条。应当触发本技能的真实说法（任务集和 JEV 调优都用）
  - 把 DAY-12 拆一下
  - 这个需求帮我拆成子任务
not-for:                              # 必填，≥ 1 条。容易混淆、但不该由本技能处理的说法，箭头后写应该去哪
  - 给 DAY-12 写实施计划 → plan-writer
tags: [dev-flow, linear]              # 选填
internal: false                       # 选填，默认 false。true = 不参与用户请求的技能选择（内部技能）
---
```

### 工具白名单语义（`allowed-tools`）

工具按权限分三级（定义在 `agent/tools/base.py` 的 `Permission`）：

| 级别 | 例子 | 没有技能命中时 | 技能命中时 |
|---|---|---|---|
| `read` 只读 | read_file、git_log、linear_get_issue、read_note | 可用 | 可用（写进白名单只是声明） |
| `write_local` 本地写 | write_file、edit_file、git_commit、run_command | **不可用** | 只有列在本轮命中技能的白名单里才可用 |
| `external` 外部可见写 | linear_create_issue、linear_update_issue | **不可用** | 同上，而且执行前一律要人工确认 |

**为什么这样设计**：技能白名单和工具门控是两道闸（对应架构文档 3.3d）。白名单决定"这个技能有没有资格用"，门控决定"这一次调用该不该放行"。只读工具默认全开，是为了不让没命中技能的普通提问（如"最近提交了啥"）因为缺工具答不上来。

白名单里写了未注册的工具名，加载时报错（`python -m agent skills` 会列出来）。

## 正文写法

正文会**整段**注入主模型的系统提示（命中时才注入），所以要短：建议 ≤ 1500 字，超出部分放 `references/`。推荐结构：

```markdown
# 技能标题

## 什么时候用
一两句话，与 description 一致。

## 步骤
1. 先探测再行动：能用只读工具查到的，不问用户。
2. ……
3. 写操作前：用 update_plan 列出将要执行的写操作。

## 输出契约
最终回复必须包含什么、用什么格式。

## 不要做
- 边界与禁止项（例如：不直接 push、不改动与 issue 无关的文件）
```

## 校验规则（`python -m agent skills` 会逐条检查）

1. `name` 为 kebab-case，且等于目录名
2. `description` 非空且 ≤ 300 字
3. `version` 符合 `x.y.z`
4. `model` ∈ {auto, local, cloud}
5. `allowed-tools` 里的每个名字都已在工具注册表里
6. `triggers` ≥ 2 条，`not-for` ≥ 1 条
7. 正文非空
