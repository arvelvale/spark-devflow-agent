01 / 结构

三层结构：元数据 → 路由器 → 细节库

一个 skill 目录里通常只有三类东西，各管一段生命周期。理解这张图，就理解了 skill 90% 的工作原理。

frontmatter

元数据 · 被选中之前发生的事

YAML 头
  • description 前堆触发词：deploy / enable / troubleshoot / shutdown / configure……「特性名不用背，触发动词在 frontmatter 里」——选择器（人或模型）只凭这段文字决定要不要加载。
  • argument-hint、tags、frameworks、domain 提供二次筛选信号。
  • compatibility 声明运行前提（仓库检出 / Docker / K8s / Python 3.11+），不满足就不该被选中。
  • allowed-tools 是权限白名单：只列只读命令前缀（Bash(docker ps *)、Bash(nvidia-smi *)……）+ Read / Grep / Glob。没有一条写操作。

SKILL.md

薄路由器 · 204 行的分流中枢

主入口
  • 意图路由表：用户意图 → 该读哪篇 reference（deploy → references/deploy.md；stop → references/shutdown.md）。
  • Configure 特性表：16 个特性关键词 → 16 篇配置文档（VLM、Guardrails、Agentic RAG、查询改写、摄取、搜索……）。
  • 配一套固定流程（探测 → 定位 → 核对 → 应用 → 验证），见第 02 节步进器。
  • 自身不带细节——细节全在 references/，所以主文件才能保持 204 行。

references/

细节库 · 用到才读的操作手册

30+ 篇
  • configure/ 16 篇（每特性一篇）+ deploy/ 10 篇（Docker / Helm / 库 / NVIDIA 托管 / 自托管等形态）+ troubleshoot + shutdown。

03 / 流程

Configure 八步：探测先于动手，变更必须验证

以「改一个 RAG 特性配置」为例。注意它的纪律：能命令探测的不问用户， 配置文件与线上服务不一致要主动指出，改完必须验证——这套流程比细节文档更值得借鉴。

04 / 模式

四个值得抄走的模式

这些模式与具体产品无关，是 skill 这种形态的通用工艺。右栏是我们项目的落点。

权限白名单 allowed-tools

技能级声明自己能调用的工具，且只给只读命令前缀。技能被误加载的最坏结果被限制在「读了几眼」，而不是「改了什么」。

我们怎么落：架构文档 3.3d 的权限分级与 skill 级 allowed-tools 组成双闸门。

探测先于提问 Autonomy

「一切自动探测：GPU、显存、驱动、Docker、端口、已有服务。凡是能用命令检查的，就直接检查——不要问用户。」只在必须用户操作（给 key、确认删除）时才问。

我们怎么落：写进内核规范，JEV 决策前的召回阶段就是代码探测。

验证闭环 Verify

每篇文档的结尾都是验证：health endpoint、rollout status、容器状态。变更不以「执行完」结束，以「验证通过」结束。

我们怎么落：架构文档第 7 节工具调用从「结果回填」升级为「执行后必须验证」。

自评五维 skill-card

Security / Correctness / Discoverability / Effectiveness / Efficiency。尤其 Discoverability（该加载时才加载）与 Effectiveness（带技能显著优于不带）——正好就是 A/B 评测的两个指标。

我们怎么落：架构文档第 12 节 A/B harness 的指标直接对齐官方口径。
